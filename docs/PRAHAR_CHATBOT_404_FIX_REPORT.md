## 4. Why the 404 Occurred: Dual Root Cause Analysis

### Root Cause 1: Vercel Static Serving of `/api/chat` (Primary Failure Mode)
* **What Happened:**
  1. The Vercel project was deployed with root directory pointing to `frontend`.
  2. In `frontend/src/api/client.js`, `API_BASE_URL` defaulted to `/api` when `VITE_API_URL` was unset in Vercel's Environment Variables.
  3. In development, Vite's `server.proxy` forwarded `/api` to `http://localhost:8080/api`.
  4. In production on Vercel, Vite's dev proxy does not exist. Vercel solely serves static files from `dist/`.
  5. There was **no `vercel.json`** file in the repository defining rewrite proxies for `/api/*` or SPA routing.
  6. The browser issued:
     ```http
     POST https://<project-name>.vercel.app/api/chat
     ```
  7. Vercel checked its static routing table for a file at `/api/chat`. No such file exists, and no serverless function exists.
  8. Vercel returned **HTTP 404 Not Found**.
  9. Axios threw: `Error: Request failed with status code 404`.
  10. `chatApi.js` caught the error and assigned:
      - `errorType = 'HTTP_ERROR'`
      - `statusCode = 404`
      - `errorMessage = 'Request failed with status code 404'`
  11. `PraharChatbot.jsx` rendered:
      ```
      Service Alert: HTTP ERROR (404)
      Request failed with status code 404
      ```

### Root Cause 2: Subpath Omission in `VITE_API_URL` (Secondary Failure Mode)
* **What Happened:**
  1. If a developer deployed the backend to a cloud host (e.g., `https://prahar-backend.onrender.com`) and configured Vercel's `VITE_API_URL` to `https://prahar-backend.onrender.com` (omitting the `/api` subpath):
  2. In `client.js`:
     ```javascript
     const API_BASE_URL = 'https://prahar-backend.onrender.com';
     client.post('/chat', payload); // Results in: https://prahar-backend.onrender.com/chat
     ```
  3. Spring Boot's `ChatController` is mapped to `@RequestMapping("/api/chat")`. It has no route handler for `/chat`.
  4. Spring Boot returned **HTTP 404 Not Found** with `{ "status": 404, "error": "Not Found", "path": "/chat" }`.

### Why URL Scanning Appeared to "Work" While Chatbot Failed
* In `frontend/src/api/scannerApi.js`:
  ```javascript
  async scanUrl(url) {
    try {
      const response = await client.post('/scans/url', { url });
      if (response.data?.data) return { data: response.data.data, source: 'BACKEND_LIVE' };
    } catch (err) {
      console.warn('Backend /scans/url fallback to local engine:', err.message);
    }
    const localResult = analyzeUrl(url); // Browser-side heuristics
    return { data: localResult, source: 'LOCAL_ENGINE' };
  }
  ```
  When `/api/scans/url` returned 404 on Vercel, the scanner caught the error and silently fell back to the client-side heuristics engine (`LOCAL_ENGINE`).
* In `frontend/src/api/chatApi.js`, however, there was no silent fallback; it threw the error directly to the chatbot UI, displaying the HTTP 404 alert.

## 7. Code Changes Implemented

### 1. `frontend/src/api/client.js`
* Added `getApiBaseUrl()` normalization logic:
  - If `VITE_API_URL` is omitted, defaults to `/api`.
  - Automatically strips trailing slashes.
  - Automatically appends `/api` if an absolute HTTP/HTTPS URL is supplied without it (e.g., `https://backend.com` -> `https://backend.com/api`).
* Increased default timeout from 4000ms to 15000ms to tolerate server cold starts.
* Updated token lookup to read `prahar_token` first, with fallback to legacy `phishshield_token`.

### 2. `frontend/src/api/chatApi.js`
* Added explicit handling for `statusCode === 404`:
  - `errorType = 'ENDPOINT_NOT_FOUND'`
  - `userFriendlyMessage = 'Chatbot endpoint not found (HTTP 404). Verify that VITE_API_URL is configured in your deployment settings and points to the live backend API ending in /api.'`
* Removed hardcoded `'port 8080'` string from network failure error message.

### 3. `frontend/src/api/notificationApi.js`
* Updated `createEventSource` to use the normalized `getApiBaseUrl()`, preventing broken SSE URLs when `VITE_API_URL` lacks `/api`.

### 4. `frontend/src/components/NotificationBell.jsx`
* Standardized token retrieval to check `prahar_token` before `phishshield_token`.

### 5. `frontend/vercel.json` (New File)
* Configured SPA fallback rewrite:

    ]
  }

### 6. `vercel.json` (Root Fallback)
* Configured root rewrite fallback to `frontend/index.html` in case Vercel is connected without setting root directory to `frontend`.

### 7. `frontend/src/tests/apiRouting.test.js` (New Test Suite)

## 9. Required Deployment Configuration on Vercel

To permanently eliminate the 404 in production, configure the deployment using one of two validated patterns:

### Option A: Direct API Integration (Recommended)
1. Deploy the Spring Boot backend to a container host (Render, Railway, AWS ECS, or Fly.io).
2. Obtain the backend HTTPS URL (e.g., `https://api-prahar.onrender.com`).
3. In the **Vercel Project Dashboard** -> **Settings** -> **Environment Variables**:
   - Add variable: `VITE_API_URL`
   - Value: `https://api-prahar.onrender.com` (or `https://api-prahar.onrender.com/api` — our `client.js` now handles both correctly).
4. In the backend host environment variables:
   - Add the Vercel domain to `CORS_ALLOWED_ORIGINS`:
     ```
     CORS_ALLOWED_ORIGINS=https://<your-vercel-domain>.vercel.app
     ```
5. Trigger a redeploy in Vercel.

### Option B: Vercel Proxy Rewrite
If you prefer not to manage cross-origin CORS headers, update `frontend/vercel.json` rewrites before the `/(.*)` rule:
```json
{
  "rewrites": [
    {
      "source": "/api/:match*",
      "destination": "https://<your-deployed-backend-url>/api/:match*"
    },
    {
      "source": "/(.*)",
      "destination": "/index.html"
    }
  ]
}
```
When using Option B, set `VITE_API_URL=/api` in Vercel. Vercel's Edge network will forward all `/api/*` calls directly to your backend host.
